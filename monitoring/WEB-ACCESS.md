# Веб-доступ к мониторингу: HTTPS + Telegram Mini App

Графики открываются по адресу `https://<MONITOR_DOMAIN>`:

- **в Telegram** — кнопкой «Мониторинг» в меню бота, который присылает алерты. Вход
  автоматический и только для аккаунтов из `TG_ALLOWED_USERS`;
- **в браузере** — по ключу доступа (`ACCESS_KEY`), один раз на 30 дней;
- **из скриптов** — с заголовком `Authorization: Bearer <ACCESS_KEY>`.

Сертификат Let's Encrypt Caddy выпускает и продлевает сам. SSH-туннель к `127.0.0.1:8428`
остаётся запасным входом на случай, если сломается веб.

## Как это устроено

```
 Telegram / браузер                монитор-сервер
┌───────────────────┐  HTTPS  ┌───────────────────────────────────────────────┐
│ мини-приложение   ├────────►│ caddy :443 ─┬─ /auth/* ──────────► gate       │
│ или вкладка       │         │  (сертификат│   (страница входа, проверка    │
└───────────────────┘         │   сам)      │    Telegram и ключа)           │
                              │             │                                │
                              │             ├─ «пускать?» (forward_auth) ► gate
                              │             │                                │
                              │             └─ белый список путей ──► victoria-metrics
                              │                (только чтение)        (+ /vmalert/*)
 ru-probe ── HTTPS + пароль ─►│ caddy ── POST /api/v1/write ───► victoria-metrics │
                              └───────────────────────────────────────────────┘
```

- **caddy** ([caddy/Caddyfile](caddy/Caddyfile)) — HTTPS и единственная дверь снаружи.
  Пропускает к VictoriaMetrics только явный список путей, которые читает vmui.
- **gate** ([gate/gate.py](gate/gate.py)) — решает, кого пускать. Python без зависимостей,
  образ не собирается, наружу не публикуется.
- Порт VictoriaMetrics по-прежнему слушает только `127.0.0.1`.

## Установка

1. **DNS.** A-запись `MONITOR_DOMAIN` (например, `monitor.horusping.com`) → IP монитор-сервера.
   Если домен у Cloudflare — запись «DNS only», без оранжевого облака.
2. **Порты.** Открыть на монитор-сервере входящие **80 и 443/tcp**. 80 нужен только для
   проверки Let's Encrypt и редиректа на HTTPS.
3. **`.env`** (всё описано в [.env.example](.env.example)):

   ```bash
   MONITOR_DOMAIN=monitor.horusping.com
   TG_ALLOWED_USERS=123456789          # ваш числовой id в Telegram, через запятую — несколько
   ACCESS_KEY=$(openssl rand -hex 32)  # для браузера; пусто — только Telegram
   ```

   Свой id: напишите боту что угодно и посмотрите `message.from.id` в
   `https://api.telegram.org/bot<TOKEN>/getUpdates` (или спросите @userinfobot).
   Это id **человека**: у групп id отрицательные, gate их не примет и скажет об этом.

4. **Start в боте.** Каждый из `TG_ALLOWED_USERS` должен хотя бы раз нажать Start в боте —
   без этого у Telegram нет чата, куда поставить кнопку.
5. **Запуск:**

   ```bash
   docker compose up -d
   docker compose logs gate caddy | tail -20
   ```

   В логе gate должно быть `gate for …: telegram on (1 user(s)), access key on, …` и
   `menu button set for Telegram user …`. В логе caddy — `certificate obtained successfully`.

**Проверка:**

```bash
curl -sI https://monitor.horusping.com/vmui/ | head -3        # 302 на /auth/?next=… — вход закрыт
curl -s -H "Authorization: Bearer $ACCESS_KEY" \
  'https://monitor.horusping.com/api/v1/query?query=up' | head -c 100   # {"status":"success",…
```

Затем откройте бота в Telegram → кнопка «Мониторинг» слева от поля ввода → дашборды.

Кнопку можно поставить и вручную (@BotFather → Bot Settings → Menu Button, адрес
`https://<MONITOR_DOMAIN>/auth/`) — тогда она видна всем пользователям бота, но войти
всё равно смогут только разрешённые. Автоматическую установку выключает `TG_MENU_BUTTON=`.

## Как пользоваться

| Что | Как |
|---|---|
| Телефон / Telegram Desktop | кнопка «Мониторинг» в боте. Каждое открытие заново входит само; сессия живёт 12 ч |
| Браузер | `https://<MONITOR_DOMAIN>/` → ключ доступа. Ссылка вида `…/vmui/#/cardinality` после входа приводит туда же |
| Скрипт | `curl -H "Authorization: Bearer $ACCESS_KEY" https://<MONITOR_DOMAIN>/api/v1/query?query=up` |
| Алерты и правила | в vmui пункт меню Alerts, или прямо `https://<MONITOR_DOMAIN>/vmalert/groups` |
| Цели скрейпа | `https://<MONITOR_DOMAIN>/targets` — у каждой видно `up` и последнюю ошибку |
| Выйти | `https://<MONITOR_DOMAIN>/auth/logout` |
| Разлогинить всех | поменять `SESSION_SALT` (или `ACCESS_KEY`) и `docker compose up -d gate` |
| Отнять доступ у человека | убрать его id из `TG_ALLOWED_USERS`, `docker compose up -d gate` — действует сразу |
| Если веб сломан | `ssh -L 8428:127.0.0.1:8428 root@<монитор>` и `http://localhost:8428/vmui` |

**Telegram Web** (web.telegram.org) показывает мини-приложение во фрейме, и там всё работает
так же. Исключение — браузер, который блокирует сторонние cookie (Chrome с такой
настройкой, окно инкогнито): он не даёт фрейму хранилища, и vmui в нём не отрисуется.
Тогда страница входа сама предложит «Открыть в новой вкладке» — одноразовая ссылка на
минуту, которая переносит вход в обычную вкладку.

## Что открыто снаружи

Только чтение. Через веб доступны vmui (запросы, дашборды, кардинальность, топ запросов,
песочницы relabeling и WITH), страницы vmalert, список целей скрейпа и настройки VM
(`/flags`). **Недоступно никак**, даже после входа: удаление рядов (`/api/v1/admin/*`),
импорт и запись (`/api/v1/import*`, `/api/v1/write`, influx, opentsdb и прочие протоколы
приёма), снапшоты, `/internal/*`, `/-/reload`, `/debug/pprof`, `/metrics`.

Пути с `..`, `//` или обратным слэшем (в том числе закодированными) отклоняются с 400 ещё
до белого списка — почему, объяснено в [Caddyfile](caddy/Caddyfile).

После повышения `VM_TAG` новая версия vmui может обратиться к пути, которого нет в списке, —
вкладка покажет 404. Путь дописывается в `@read` в Caddyfile.

## Пробник из России через тот же HTTPS

Если стоит [ru-probe](ru-probe/): на монитор-сервере задать `PROBE_PASSWORD`
(`openssl rand -hex 24`) и `docker compose up -d gate`; на пробнике в `.env`:

```bash
MONITOR_URL=https://monitor.horusping.com
MONITOR_PASSWORD=<тот же PROBE_PASSWORD>
```

Маршрут открывает только `POST /api/v1/write` и только с этим паролем; сессия браузера или
ключ доступа его не открывают. Пока `PROBE_PASSWORD` пуст, маршрута нет вовсе. Открывать
порт VictoriaMetrics наружу и включать ей `-httpAuth.*` больше не нужно.

## Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| Сертификат не выпускается (в логе caddy `challenge failed`, `timeout`) | A-запись не указывает на сервер, закрыт порт 80, или домен проксирует Cloudflare. `docker compose logs caddy` |
| На всё отвечает 502 | gate не запущен. `docker compose logs gate` — он пишет, что не так в `.env`, и не стартует, пока не исправлено (например, если никто не смог бы войти) |
| В боте нет кнопки | Не нажат Start. В логе gate: `refused (400 Bad Request: chat not found)`. Нажмите Start и `docker compose restart gate` |
| «Этому аккаунту Telegram вход не разрешён» | id нет в `TG_ALLOWED_USERS` |
| «Данные входа от Telegram устарели» | Мини-приложение было открыто больше часа назад. Закройте и откройте снова |
| «Не прошли проверку подписи» | Приложение открыто из другого бота, чем тот, чей `TELEGRAM_BOT_TOKEN` в `.env` |
| «Слишком много неудачных попыток» | 10 ошибок с адреса за 15 минут. Подождать или `docker compose restart gate` |
| Вкладка vmui пустая, в ответах 404 | Путь не в белом списке (обычно после смены `VM_TAG`) — см. выше |
| Пробник: `unexpected status code 401` | `MONITOR_PASSWORD` на пробнике ≠ `PROBE_PASSWORD` на мониторе |
| Пробник: 404 | `PROBE_PASSWORD` на мониторе пуст — маршрут выключен |

## Тесты

```bash
cd monitoring/gate && python3 -m unittest -v
# без локального Python:
docker run --rm -v "$PWD":/g -w /g python:3.13-alpine python -m unittest -v
```

Проверяют подпись initData (включая «чужой» токен и ключ Login Widget вместо Mini App),
сессии, одноразовые ссылки, тормоз перебора, конфигурацию и HTTP-контракт, на который
опирается Caddyfile.

## Решения и почему

1. **HTTPS — Caddy, а не nginx + certbot**, как в основном стеке. Сертификат выпускается и
   продлевается сам, без entrypoint-скриптов и цикла продления; `forward_auth` встроен;
   весь конфиг — один файл. Монитор — отдельный compose-проект на отдельной машине, так
   что единообразие с главным сервером ничего не даёт, а скрипты certbot — лишняя
   поверхность для ошибок. Только HTTP/1.1 и HTTP/2: HTTP/3 потребовал бы ещё и UDP 443.
2. **Авторизация — свой маленький сервис `gate`.** Готовые прокси (oauth2-proxy, Authelia)
   не умеют Telegram. Python только из стандартной библиотеки: образ не собирается,
   зависимостей нет, вся логика безопасности — один читаемый файл. Контейнер read-only,
   не root, без capabilities.
3. **Белый список путей, а не чёрный.** Проверено на живой VictoriaMetrics v1.111.0:
   `delete_series` выполняется обычным GET (ответ 204) — достаточно ссылки. Список собран
   по реальному бандлу vmui этой версии и подтверждён обходом всех вкладок в браузере: ни
   один запрос vmui не упирается в список. Так нашёлся `/flags`, который vmui читает на
   каждой вкладке.
4. **Отдельная защита от обхода белого списка.** Caddy сопоставляет `path_regexp` с
   *очищенным* путём, а VictoriaMetrics отдаёт *сырой*: `/api/v1/admin/tsdb/delete_series/../../../query`
   для Caddy выглядит как разрешённый `/api/v1/query`. VictoriaMetrics к тому же склеивает
   `//`. Поэтому любой путь с `..`, `//` или `\` (включая `%2e%2e`, `%2F`, `%5C`)
   отклоняется до белого списка. Query-строку правило не трогает.
5. **Сессия — подписанная cookie, без хранилища.** Ключ подписи выводится из токена бота,
   `ACCESS_KEY` и `SESSION_SALT`: нечего хранить, сессии переживают перезапуск. Смена
   `ACCESS_KEY` разлогинивает все браузеры, `SESSION_SALT` — всех вообще, без смены
   секретов. Токен бота и так позволяет подделать данные Telegram, так что опора на него
   ничего не ослабляет.
6. **Cookie `__Host-`** (только Secure, только этот хост). В приложении Telegram и в
   браузере — `SameSite=Lax`: чужой сайт не заставит браузер отправить её со своим
   запросом. В Telegram Web мини-приложение живёт во фрейме, где Lax-cookie не
   отправляется вовсе, — там `SameSite=None; Partitioned`: cookie лежит в отдельной
   «банке», привязанной к web.telegram.org, и больше нигде не отправляется. Остаточный риск:
   другое мини-приложение, открытое в том же Telegram Web, может слать запросы с этой
   cookie. Прочитать ответы оно не может (CORS-заголовки срезаны), а менять через белый
   список нечего — поэтому он и только на чтение.
7. **Сессии проверяются по текущему конфигу на каждом запросе.** Убрали id из
   `TG_ALLOWED_USERS` или очистили `ACCESS_KEY` — доступ пропадает сразу, а не когда
   истечёт cookie.
8. **Сроки.** Telegram — 12 часов: каждое открытие мини-приложения входит заново само, так
   что короткий срок ничего не стоит. Ключ — 30 дней: его вводят руками. Данные запуска
   от Telegram принимаются не старше часа.
9. **Подпись Telegram** — `HMAC_SHA256(key="WebAppData", msg=токен)`, не `SHA256(токен)` от
   Login Widget: их путают, и тест это ловит. Поле `signature` принимается и учтённым в
   строке проверки (как в документации), и неучтённым — оба варианта всё равно подписаны
   токеном бота, а расхождение клиентов не должно запирать владельца.
10. **Без `telegram-web-app.js`.** Данные запуска берутся из `#tgWebAppData`, события
    ready/expand отправляются так же, как это делает официальный скрипт. На странице входа
    нет чужого кода (CSP `script-src 'self'`), а в обычном браузере она не ждёт telegram.org.
11. **Кнопка меню ставится автоматически и адресно** — `setChatMenuButton` в чате каждого
    разрешённого пользователя. Остальные пользователи бота её не видят.
12. **Telegram Web с запрещёнными сторонними cookie.** Партиционированная cookie там
    работает, но фрейму запрещён `localStorage`, и vmui (обращается к нему без проверки)
    остаётся белым листом. Исправить vmui нельзя, поэтому страница входа видит запрет и
    предлагает одноразовую ссылку на 60 секунд в новую вкладку. Одноразовость хранится в
    памяти gate — после перезапуска ссылки всё равно мертвы через минуту. Формат ссылки
    (`h1.*`) не принимается как сессия, и наоборот.
13. **Тормоз перебора** — 10 неудач с адреса за 15 минут, дальше 429 (форма ключа,
    Bearer, пароль пробника). Запрос вовсе без учётных данных попыткой не считается.
14. **Отказ — закрыт.** Упал gate — Caddy отвечает 502 на всё, включая запись пробника.
    gate не стартует с конфигом, при котором никто не смог бы войти, и с id группы вместо
    id человека.
15. **Ключ для скриптов** — `Authorization: Bearer <ACCESS_KEY>` на любой запрос; тот же
    тормоз перебора.
16. **Пробник пишет через тот же HTTPS.** Раньше для него предлагалось открыть порт
    VictoriaMetrics в интернет с `-httpAuth.*` — теперь порт VM не публикуется никогда,
    запись идёт через Caddy по паролю, который открывает только её.
17. **Страницы vmalert в vmui** (`-vmalert.proxyURL`): правила и то, что горит прямо
    сейчас, — главное, что хочется видеть с телефона. `-external.url` vmalert теперь
    указывает на веб-адрес, так что ссылки на алерт ведут туда же, через вход.
18. **Гигиена Caddy:** HSTS, `Referrer-Policy: no-referrer`, `noindex`, без заголовка
    `Server`, CORS-заголовки VictoriaMetrics срезаются, `Cookie` и `Authorization` до неё
    не доходят, access-логов нет — в них нечему утечь. Фреймить страницы может только
    web.telegram.org.
19. **SSH-туннель остаётся** — порт 8428 на `127.0.0.1` как аварийный вход, если сломаются
    сертификат или gate.
20. **Служебные `/auth/check*` снаружи не видны** (404): это точки для `forward_auth`, а не
    для интернета — незачем давать лишний «оракул» для подбора.
21. **Адрес клиента для тормоза** gate берёт из `X-Forwarded-For`, который Caddy
    перезаписывает сам: проверено, что подставной заголовок тормоз не обходит. Поэтому gate
    нельзя публиковать мимо Caddy.
22. **Тело POST gate дочитывает всегда**, даже отказывая сразу. Соединение Caddy → gate
    постоянное, и недочитанное тело стало бы началом чужого следующего запроса. Слишком
    большое тело — 413 и закрытое соединение. На это есть тест.

Замерено на тестовом стенде: Caddy ~24 МБ RAM, gate ~17 МБ.

**Как проверялось.** Настоящий `docker-compose.yml` этого каталога поднимался целиком
(VictoriaMetrics, vmalert, Alertmanager, gate, Caddy; сертификат — от локального CA Caddy
вместо Let's Encrypt). Сверху — 60 проверок curl (редиректы, вход по ключу и Bearer, каждый
путь белого списка, каждый опасный путь и шесть вариантов обхода с живой сессией, запись
настоящим `vmagent` с верным и неверным паролем, падение gate) и 21 сценарий в Chromium:
вход из Telegram как в приложении (с темой и событиями ready/expand), чужой аккаунт,
устаревшие данные, ключ с сохранением `#/cardinality`, обход всех вкладок vmui без единого
отказа, Telegram Web во фрейме — с разрешёнными и с запрещёнными сторонними cookie, запрет
фрейминга чужим сайтом. Проверить с настоящим Telegram и настоящим Let's Encrypt в
песочнице было нельзя — это первое, что стоит сделать после выкладки.
