# Horus — мониторинг

VictoriaMetrics + vmalert + Alertmanager. Веб-морда с графиками за любой период,
алерты в Telegram, метрики со всех серверов и их контейнеров.

Без Prometheus (VictoriaMetrics скрейпит сама) и без Grafana (у vmui есть
кастомные дашборды). На всё про всё ~350 МБ RAM и ~500 МБ диска за 30 дней.

## Почему на отдельном сервере

Не ради ресурсов. Сторож, который живёт на охраняемом объекте, не может сообщить,
что объект сгорел. Алерт «главный сервер не отвечает» обязан приходить откуда-то
ещё. Подойдёт самый дешёвый VPS: 1 vCPU / 1 ГБ / 10 ГБ.

Если ставить всё-таки на главный — работать будет, но вы не узнаете о его
падении. Тогда заведите внешний dead-man switch (healthchecks.io и подобные).

## Модель: pull, не push

VictoriaMetrics сама ходит к каждому серверу по тому TLS-порту, который там уже
открыт, на пути `/metrics/*`, закрытые basic-auth. На ноды не ставится ни
vmagent, ни vector — только экспортёры.

Побочный эффект, ради которого это и сделано: **неудавшийся скрейп — это уже
алерт** (`up == 0`). В push-модели упавший сервер просто замолкает, а молчание
неотличимо от «всё хорошо».

```
монитор-сервер                 главный / нода
┌──────────────────┐   HTTPS   ┌──────────────────────────────┐
│ victoria-metrics ├──────────►│ nginx  /metrics/host         │→ node-exporter
│  + vmui          │  basic    │        /metrics/containers   │→ cadvisor
│ vmalert          │   auth    │        /metrics/agent        │→ node-agent (только нода)
│ alertmanager ────┼──► TG     └──────────────────────────────┘
└──────────────────┘
```

## Что и откуда берётся

| Источник | Даёт | Где живёт |
|---|---|---|
| node-exporter | CPU, RAM, swap, диск, сеть, OOM-kill | везде |
| cadvisor | CPU/память по контейнерам | главный — да, ноды — по желанию |
| node-agent `/metrics` | xray, пользователи, трафик по инбаундам, комнаты olcrtc, срок сертификата | только ноды |

Метрики агента не стоят ни одного нового процесса: эндпоинт живёт в уже
работающем агенте и отдаёт снимок, который монитор подключений и так снимает
каждые 20 секунд. Скрейп никогда не дёргает xray — иначе нагруженная нода
получала бы от мониторинга дополнительную нагрузку ровно тогда, когда ей хуже
всего.

## Установка

Пошагово, с проверками и подводными камнями — **[DEPLOY.md](DEPLOY.md)**. Ниже короткая
выжимка; если ставите впервые, идите по DEPLOY.md: там первым пунктом слияние веток, без
которого серверы притянут старый код.

### 1. Монитор-сервер

```bash
git clone <repo> /opt/horus && cd /opt/horus/monitoring
cp .env.example .env

# Токен для скрейпа — ОДИН на весь парк серверов.
# tr -d '
': a trailing newline in a password file is a coin flip across
# implementations, and a scrape that fails on 401 looks like a dead server.
openssl rand -hex 24 | tr -d '
' > vm/secrets/metrics_password
chmod 600 vm/secrets/metrics_password

# Telegram: бот от @BotFather, chat_id из
# https://api.telegram.org/bot<TOKEN>/getUpdates
nano .env          # TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID

docker compose up -d
```

### 2. Каждый сервер, который надо мониторить

Один и тот же токен, что и в `vm/secrets/metrics_password`:

```bash
echo 'METRICS_TOKEN=<тот же токен>' >> .env
docker compose up -d --build nginx          # nginx пересобирается: нужен htpasswd
docker compose up -d
```

Пустой `METRICS_TOKEN` = `/metrics/*` отвечает 404. Сервер, которому ничего не
настроили, не начинает публиковать телеметрию сам по себе.

### 3. Прописать серверы

`targets/hosts.yml`, `targets/agents.yml`, `targets/containers.yml` — обычные
списки. VictoriaMetrics перечитывает их раз в минуту: добавление сервера ничего
не требует перезапускать.

Имя в `targets` должно быть тем, которое **покрывает сертификат** сервера.
Сертификат на другое имя роняет скрейп с ошибкой x509, и это выглядит как
«сервер лёг».

### 4. Открыть графики

vmui слушает только `127.0.0.1` — у VictoriaMetrics **нет аутентификации**.

```bash
ssh -L 8428:127.0.0.1:8428 root@<монитор>
```

и `http://localhost:8428/vmui` → вкладка **Dashboards** → «Horus — серверы» и
«Horus — сервис».

## Алерты

`vmalert/rules/infra.yml` — хост: недоступность, CPU, steal, RAM, swap, OOM-kill,
диск (включая «кончится в ближайшие сутки»), насыщение гигабитного канала,
ошибки интерфейса, read-only ФС.

`vmalert/rules/horus.yml` — сервис: xray не отвечает; **xray не держит ни одного
пользователя при непустом локальном списке** (та самая авария, где все метрики
зелёные, а подключиться нельзя); профиль не отрендерился; онлайн есть, а трафика
нет; комнаты olcrtc — по одной и все сразу; флапающая комната; сертификат
истекает; **сертификат не покрывает имя ноды**; контейнер у своего лимита памяти;
контейнер в цикле перезапуска.

Alertmanager группирует по серверу, давит дубли (упавший сервер = одно
сообщение, а не девять) и повторяет: critical раз в 2 часа, warning раз в 12.

## Проверка после установки

```bash
# Цели: все должны быть up
curl -s localhost:8428/api/v1/targets | jq '.data.activeTargets[] | {job:.labels.job, server:.labels.server, health}'

# Правила загрузились
curl -s localhost:8880/api/v1/rules | jq '.data.groups[].name'

# Телеграм живой — временно уроните что-нибудь безобидное, например
# остановите node-exporter на одной ноде и дождитесь ServerUnreachable (3 мин).
```

## Блокировка узла по IP

Проверить блокировку российским провайдером с зарубежного сервера **невозможно в принципе** —
нужен сетевой обзор изнутри страны. Поэтому сигналов два, и первый ничего не стоит.

### Косвенный — работает сразу, ставить нечего

`vmalert/rules/blocking.yml`, правило **NodeReachableButNobodyConnects**: узел здоров, xray
отвечает, метрики собираются — и ни одного пользователя онлайн, при том что **последние шесть
часов они были**. Именно эта оговорка отделяет блокировку от ночного затишья и от свежего
узла, на который ещё никто не пришёл.

Рядом **NodeOnlineCollapsed** — онлайн упал вчетверо. Ловит частичную блокировку, когда режет
часть операторов, а остальные ещё доходят.

### Прямой — нужен маленький VPS в России

`ru-probe/` — blackbox-exporter и vmagent, которые раз в минуту пытаются открыть TCP к каждому
узлу и **пушат** результат на монитор-сервер. Видит блокировку раньше, чем её увидят
пользователи.

```bash
scp -r monitoring/ru-probe root@<ru-vps>:/opt/horus-probe
ssh root@<ru-vps> 'cd /opt/horus-probe && cp .env.example .env && nano .env && docker compose up -d'
```

Прописать узлы в `ru-probe/targets/nodes.yml`. **Метка `server` обязана совпадать** с
`monitoring/targets/hosts.yml`: алерт `NodeBlockedFromRussia` сопоставляет пробу с узлом
именно по ней, и при расхождении не сработает никогда — молча.

Три решения, которые стоит проговорить:

- **Пробник пушит, а не отдаёт.** Иначе пришлось бы открыть на нём порт и завести туда доступ
  с монитора. Так он делает одно исходящее соединение и не слушает ничего.
- **Пробник не знает ничего, кроме адресов и портов.** Ни ключей узлов, ни доступа к API.
  Хостинг в РФ — другой правовой контур, и содержимое этой машины должно быть таким, чтобы её
  изъятие ничего не значило.
- **Проверяется только TCP-рукопожатие.** Не HTTP и не TLS: на 443 стоит REALITY, который
  непрошеному гостю отвечает как чужой сайт, а на 8443 — QUIC, которого blackbox не умеет.
  Вопрос проще: доходит ли до адреса хоть что-нибудь.

Алерт `NodeBlockedFromRussia` срабатывает только когда **проба не проходит, а мы узел видим**.
Если узел не отвечает и нам — это авария, о ней кричит `ServerUnreachable`, и смешивать две
совершенно разные ситуации нельзя.

### Что нужно включить на монитор-сервере

У VictoriaMetrics **нет аутентификации**, а пробнику надо писать в неё снаружи. Поэтому перед
тем, как открывать порт:

```yaml
# monitoring/docker-compose.yml, сервис victoria-metrics
command:
  - -httpAuth.username=horus
  - -httpAuth.password=<тот же, что MONITOR_PASSWORD у пробника>
```

и `VM_BIND=0.0.0.0` в `.env`. Тогда vmalert тоже надо снабдить
`-datasource.basicAuth.*` и `-remoteWrite.basicAuth.*` — он ходит в ту же VictoriaMetrics.

**Открывать порт без `-httpAuth.*` нельзя**: наружу смотрит и запись метрик, и vmui, и API
удаления рядов.

### Третий сигнал, если захочется

`https://reestr.rublacklist.net/api/v3/ip/<ip>/` отвечает, внесён ли адрес в реестр. Дёшево и
однозначно, но ловит только внесение: ТСПУ душит и невнесённые адреса, а внесение может
опоздать на сутки. Годится как подсказка в тексте алерта, но не как датчик.

## Чего здесь пока нет

Логов. `/metrics` отвечает на «сколько» и «когда», но не на «что было написано в
логе». Под это в семействе VictoriaMetrics есть VictoriaLogs + fluent-bit
(~25 МБ на сервер) — отдельный шаг, он же заодно снимет часть нагрузки с
десятигигабайтных дисков нод, если после него понизить `LOG_MAX_SIZE`.
